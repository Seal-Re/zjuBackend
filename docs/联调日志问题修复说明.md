# 联调日志问题修复说明

基于联调 Java 日志中暴露的问题，完成以下修复与补充。

---

## 一、日志中暴露的问题与对应修复

### 1. `cases` 空指针导致创建计划失败（case 解析问题）

**现象**：
```text
java.lang.NullPointerException: Cannot invoke "java.util.List.iterator()" because "cases" is null
  at ExeStepServiceImpl.conveyTestStep2ExeStep(ExeStepServiceImpl.java:96)
```

**原因**：  
在从「测试功能 → 模块 → 子用例(case) → 步骤」生成执行步骤时，若某模块下**没有子用例**（或查询失败），`getByModuleId().getData()` 为 `null`，`objectMapper.convertValue(..., List)` 得到 `null`，后续 `for (TestFunctionCase testCase : cases)` 触发 NPE。步骤列表 `steps` 同理。

**修复**：  
- 文件：`fastop-service/.../ExeStepServiceImpl.java`  
- 对 `modules`、`cases`、`steps` 做空指针防护：  
  - 取 `getData()` 后先判空再 `convertValue`；  
  - 若结果为 `null`，使用 `Collections.emptyList()`，再遍历。  
- 这样在「模块下无 case、case 下无 step」或查询失败时，不再抛 NPE，创建计划可正常完成。

---

### 2. `fun_id in ()` SQL 语法错误

**现象**：
```text
You have an error in your SQL syntax; check the manual ... near ')' at line 16
SQL: ... from test_function WHERE ( fun_id in )
```

**原因**：  
某处调用 `getTestFunctionListById(funIds)` 时传入 **null 或空列表**，MyBatis 生成 `fun_id in ()`，在 MySQL 中非法。

**修复**：  
- 文件：`fastop-service/.../TestFunctionServiceImpl.java`  
- 在 `getTestFunctionListById` 开头增加：  
  `if (funIds == null || funIds.isEmpty()) return Collections.emptyList();`  
- 避免使用空列表构造 `andFunIdIn(funIds)`，不再出现 `fun_id in ()`。

---

### 3. 操作日志表不存在导致 500 与列表失败

**现象**：  
- `Table 'autosys_1014.operation_log' doesn't exist`  
- 操作日志列表接口报错，前端系统日志页打开即报错；  
- 其他业务（如派发、开始、暂停）在写操作日志时落库失败，仅 WARN，不影响主流程。

**修复**：  
1. **后端降级**  
   - 文件：`fastop-service/.../OperationLogServiceImpl.java`  
   - 在 `list()` 中对「查询 operation_log」做 try-catch：  
     - 异常时打 WARN（提示执行 `dataset/operation_log.sql`），并返回 `{ list: [], total: 0 }`，不再向调用方抛异常。  
   - `record()` 原有 try-catch 保持不变，落库失败仅 WARN，仍返回成功。  

2. **建表脚本**  
   - 新增：`fastop/dataset/operation_log.sql`  
   - 建表语句与 `OperationLogMapper.xml` / `OperationLog` 实体一致（id, operator_id, operator_name, module, action, target_type, target_id, detail, ip, create_time）。  
   - 使用方式：在目标库执行该脚本即可创建 `operation_log` 表；未建表时接口已降级，不再 500。

### 4. 前端系统日志页响应结构与错误态

**问题**：  
- 请求层拦截器已统一返回 `res.data`，系统日志页仍用 `res?.data ?? res` 取数，易与当前后端返回的 `{ list, total }` 不一致。  
- 操作日志接口在表不存在时曾返回 500，前端仅 catch 置空列表，未区分「无数据」与「接口异常」，且无提示。

**修复**：  
- 文件：`frontend/src/views/review/SystemLogs.vue`  
- **操作日志**：  
  - 按「拦截器已返回 data」处理：以 `res` 为业务数据，`data.list` / `data.total`；兼容 `res` 直接为数组的情况。  
  - catch 时置空列表与 total，并 `console.warn` 提示（如「操作日志加载失败（可能未建 operation_log 表）」），便于排查。  
- **执行日志**：  
  - 同样按 `res` 即 data 处理 `list`/`total`，并兼容数组；catch 时置空并 `console.warn`。  

这样在表未建或接口异常时，页面展示空列表且不报红，同时控制台有明确提示。
